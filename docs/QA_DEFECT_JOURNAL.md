# GP Work QA defect journal

Этот журнал фиксирует первопричину каждого найденного класса дефектов, системное исправление и защиту от возврата. Статус `закрыт локально` не означает production-ready: PostgreSQL E2E, CI, test deploy и повторные циклы учитываются отдельно.

## 2026-09-05 — текущий цикл `codex/worker-day-cycle-v2`

### QA-001 — дата бизнеса зависела от UTC/часового пояса сервера

- Симптом: около полуночи в Уральске dashboard, маршруты и отчёты могли показывать предыдущий день; frontend использовал UTC через `toISOString()`.
- Первопричина: несколько независимых реализаций «сегодня» на backend и frontend.
- Исправление: единая бизнес-дата `Asia/Oral`, строгая проверка календарной даты, единый расчёт дня/недели/месяца во всех затронутых модулях.
- Regression: unit-тесты границы Oral/UTC, перехода недели через месяц, високосного февраля и несуществующей даты.
- Статус: закрыт локально.

### QA-002 — водовоз попадал на недоступный dashboard

- Симптом: после входа роль `WATER_CARRIER` перенаправлялась на `/admin`, где API возвращал `403`.
- Первопричина: домашний маршрут не учитывал специализированную роль; пункт dashboard был виден без ограничения.
- Исправление: домашний маршрут водовоза — `/admin/watering`; недоступный dashboard скрыт и защищён.
- Regression: автоматический тест матрицы маршрутов проверяет доступ водовоза только к поливу и запрет dashboard/tasks.
- Статус: закрыт локально.

### QA-003 — доказательством считалась произвольная строка URL

- Симптом: Face, фото ДО/ПОСЛЕ и фото смены можно было записать ссылкой на внешний или отсутствующий файл.
- Первопричина: бизнес-методы доверяли URL из DTO и не связывали его с UploadsService.
- Исправление: все новые evidence-ссылки проверяются как файл GP Work: допустимый путь/origin, безопасное имя, существование, ненулевой размер и совпадение magic bytes с расширением.
- Regression: тесты реального сохранённого JPEG, отсутствующего файла, внешнего origin и path traversal.
- Статус: закрыт локально.

### QA-004 — Face/liveness допускал один кадр и не имел пути пересъёмки

- Симптом: API принимал один кадр; отклонённый Face всё равно позволял начать работу; мобильный экран скрывал пересъёмку.
- Первопричина: DTO и сервис проверяли только наличие evidence, не статус и не три уникальных кадра.
- Исправление: ровно три разных кадра; отклонённый последний Face блокирует start/complete; причина отклонения обязательна; worker UI позволяет пройти три кадра заново.
- Regression: PostgreSQL E2E отклоняет Face без причины, блокирует старт после отклонения и продолжает только после новой тройки кадров.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-005 — результаты смены не валидировались и не сохранялись как данные

- Симптом: вложенные проценты обходили validation; неизвестные/повторные задачи и результаты других участков искажали общий процент; детали существовали только внутри audit event.
- Первопричина: отсутствовали `ValidateNested`, проверка области задач и отдельная колонка результатов.
- Исправление: отдельный DTO закрытия, nested validation, проверка дублей/назначения/полноты, обязательные описание и причина частичного выполнения, JSONB `task_scope` и `task_results`, расчёт процента только из проверенного набора.
- Regression: PostgreSQL E2E проверяет forged URL, процент `101`, дубли, сохранение результата и идемпотентное повторение.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-006 — возвращённая смена была тупиковым состоянием

- Симптом: после `RETURNED` работник не видел смену и не мог повторно отправить исправление.
- Первопричина: state искал только `OPEN`, а close разрешал только первое закрытие.
- Исправление: `RETURNED` снова отображается с причиной; разрешена доказательная повторная отправка; статус возвращается в `CLOSED`; приёмка разрешена только завершённой смене; возврат без причины запрещён.
- Regression: E2E проходит `CLOSED → RETURNED → RESUBMITTED → REVIEWED` и проверяет запрет возврата без причины.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-007 — физический QR и детальная задача были двумя несвязанными потоками

- Симптом: `/field/scan/:sectionCode` открывал смену, но не переводил к реальному task execution с QR/GPS/Face/фото/чек-листом.
- Первопричина: экран смены показывал задачи текстом без действий.
- Исправление: каждая задача в открытой смене ведёт в существующее execution либо в QR/GPS-подтверждение с уже проверяемым кодом физического участка.
- Regression: web production build и PostgreSQL E2E полного field cycle; интерактивный browser smoke остаётся обязательным.
- Статус: закрыт по коду, browser smoke не доказан.

### QA-008 — детальное выполнение автоматически записывало `100%`

- Симптом: work log сохранял `100%`, хотя worker не передавал результат; после доработки журнал оставался со старыми данными.
- Первопричина: completion DTO не содержал результата, а запись была захардкожена.
- Исправление: completion принимает только явно подтверждённые 100%, обязательное описание и фактический объём; execution хранит эти поля; повторная отправка обновляет ту же work-log запись и сбрасывает её на повторную проверку; после возврата требуется новое фото ПОСЛЕ.
- Regression: E2E запрещает старый пустой payload, проверяет возврат с причиной, запрет повторной отправки без нового фото, обновление work log без дубля и итоговый `APPROVED`.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-009 — скрытый пункт меню не защищал URL

- Симптом: роль могла вручную открыть скрытую admin-страницу и получить экран с `403`/failed requests.
- Первопричина: role filtering существовал только в `AdminLayout`, а большинство nested routes наследовали слишком широкий guard.
- Исправление: единая `ADMIN_ROUTE_ROLES` применяется и к меню, и к каждому маршруту.
- Regression: dependency-free Node test проверяет водовоза, Акимат/Антикор и наследование ADMIN директором.
- Статус: закрыт локально.

### QA-010 — отказ карты скрывал весь dashboard

- Симптом: необязательный запрос диспетчерской карты в `Promise.all` переводил всю страницу в error state, даже когда основная сводка была доступна.
- Первопричина: обязательная и дополнительная части экрана имели общую точку отказа.
- Исправление: dashboard сохраняет основную бизнес-сводку и показывает отдельное предупреждение о карте.
- Regression: TypeScript production build; компонентный browser test ещё требуется.
- Статус: закрыт по коду, browser smoke не доказан.

### QA-011 — поддельная будущая дата обходила новое фото после возврата

- Симптом: заранее загруженное фото ПОСЛЕ с будущим `capturedAt` могло считаться доказательством исправления после возврата.
- Первопричина: свежесть доказательства сравнивалась по времени, присланному мобильным клиентом.
- Исправление: повторное завершение использует неизменяемый серверный `createdAt` загрузки фото.
- Regression: PostgreSQL E2E заранее загружает фото с будущей датой и доказывает, что завершение всё равно запрещено до новой серверной загрузки.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-012 — пустые HTML-действия не имели системной защиты

- Симптом: ручной поиск мог пропустить декоративную кнопку, пустой `onClick` или ссылку `href="#"`.
- Первопричина: production build проверяет типы, но не доказывает наличие действия у HTML-контрола.
- Исправление: AST-аудит всех TSX-файлов проверяет кнопки, submit-контекст и реальные цели ссылок.
- Regression: `npm run test:web:actions` выполняется локально и в CI.
- Статус: ожидает первый полный прогон.

### QA-013 — liveness-доказательства смены терялись и могли переиспользоваться

- Симптом: смена сохраняла только число кадров, а отклонённую Face verification можно было повторить теми же файлами под новым operation id.
- Первопричина: URL стартового/финального liveness не входили в модель смены, а свежесть кадров не проверялась системно.
- Исправление: три кадра вместе с основным селфи сохраняются в JSONB и audit event; кадры нового этапа не могут пересекаться с ранее использованными; после возврата нужны новые liveness-кадры и хотя бы одно новое фото результата; приёмка показывает все доказательства.
- Regression: unit-тесты общего liveness-правила и PostgreSQL E2E на повторное использование, сохранение и доказательную повторную отправку.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-014 — password hash мог попасть во вложенные API-ответы

- Симптом: `/users` вручную маскировал hash, но другие запросы возвращают связанные `user`/`worker` сущности напрямую.
- Первопричина: `passwordHash` был обычной selectable TypeORM-колонкой; безопасность зависела от ручного mapping каждого endpoint.
- Исправление: колонка глобально `select: false`, а login явно запрашивает hash только для bcrypt; минимальный новый пароль увеличен с 4 до 8 символов в API и UI.
- Regression: полный E2E продолжает логиниться, отклоняет пароль из 4 символов и проверяет отсутствие `passwordHash` в user/execution JSON.
- Статус: ожидает PostgreSQL E2E в CI.

### QA-015 — E2E нарушал реальный batch-контракт загрузки и упирался в throttling

- Симптом: PostgreSQL E2E падал с `429` во второй цепочке после успешных build, migrations и первого business flow.
- Первопричина: тест загружал каждый liveness-кадр отдельным запросом, тогда как API и UI поддерживают до 10 файлов в одном запросе; общий IP теста превышал лимит 20 запросов/мин.
- Исправление: E2E загружает связанные кадры пакетами так же, как production web, не ослабляя rate limit.
- Regression: обе доказательные цепочки должны пройти подряд с production throttling guard.
- Статус: ожидает повторный PostgreSQL CI.

### QA-016 — удаление сотрудника разрушало или блокировало связанную историю

- Симптом: UI предлагал hard delete, хотя смены, executions и Face evidence имеют `RESTRICT`, а часть старых связей — `SET NULL`/`CASCADE`; результатом могли быть `500` или потеря связности аудита.
- Первопричина: lifecycle учётной записи смешивал блокировку и физическое удаление.
- Исправление: DELETE стал восстановимой деактивацией; UI оставляет единое блокировать/разблокировать; запрещены самоблокировка, самопонижение и отключение последнего ADMIN/DIRECTOR.
- Regression: PostgreSQL E2E проверяет, что DELETE сохраняет строку, запрещает login и не позволяет отключить текущего администратора.
- Статус: ожидает E2E.

### QA-017 — контрольные роли появлялись как исполнители задач

- Симптом: `AKIMAT`, `ANTICOR` и `DIRECTOR` могли попасть в dropdown назначения задач.
- Первопричина: assignees исключал только `ADMIN` вместо allowlist полевых ролей.
- Исправление: endpoint возвращает только активных WORKER, WATER_CARRIER, BRIGADIER и AGRONOMIST.
- Regression: PostgreSQL E2E проверяет исключение контрольной роли.
- Статус: ожидает E2E.

### QA-018 — пробельные ФИО/логин проходили DTO и становились пустыми после trim

- Симптом: `"   "` удовлетворял `IsNotEmpty`, затем service сохранял пустое значение после `.trim()`.
- Первопричина: нормализация выполнялась после validation.
- Исправление: ФИО и логин trim-ятся через `Transform` до проверки; новые пароли минимум 8 символов и содержат хотя бы один непробельный символ.
- Regression: PostgreSQL E2E отклоняет создание пользователя с пробельным ФИО.
- Статус: ожидает E2E.

### QA-019 — состав бригады расходился между двумя источниками

- Симптом: `brigade_members` и `users.brigade_id` показывали разный состав после редактирования пользователя или повторного сохранения бригады; permissions использовали устаревший `brigadeId`.
- Первопричина: синхронизация добавляла новые связи, но не очищала старые, и выполнялась неатомарно.
- Исправление: обе стороны обновляются в одной транзакции; ответ бригады строится из канонического `users.brigade_id`; проверяются существование, активность и полевая роль; бригадир автоматически входит в состав и обязан иметь роль BRIGADIER.
- Regression: PostgreSQL E2E проверяет состав и запрет контрольной роли в качестве бригадира.
- Статус: ожидает E2E.

### QA-020 — удаление бригады могло оборвать действующие связи

- Симптом: UI вызывал физический DELETE без error handling, хотя задачи, маршруты и сотрудники ссылаются на бригаду.
- Первопричина: lifecycle смешивал удаление справочника и прекращение активности.
- Исправление: DELETE/кнопка выполняют деактивацию, история и связи остаются; UI показывает статус, loading/error/empty/success и позволяет восстановить бригаду.
- Regression: PostgreSQL E2E проверяет `isActive=false` после DELETE при сохранении задачи и состава.
- Статус: ожидает E2E.

### QA-021 — legacy WorkForm позволял анонимно создавать недоказанные work logs

- Симптом: публичный `POST /work-logs` принимал произвольные ФИО, участок, процент, GPS-флаг и URL фото без login, назначения, geofence, Face, checklist или stored-file validation.
- Первопричина: старая QR-форма осталась параллельным write-flow после появления evidence execution.
- Исправление: анонимный/manual write endpoint и неиспользуемый `tasks/open` удалены; legacy URL после авторизации перенаправляется в единственный `/field/scan/:sectionCode` flow.
- Regression: PostgreSQL E2E доказывает `404` для удалённого `POST /work-logs` и `401` для анонимного чтения участка; production build доказывает защищённый legacy redirect.
- Статус: ожидает E2E и browser smoke.
